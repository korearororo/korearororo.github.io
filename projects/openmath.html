실행 방법과 원본 데이터

실제 검색 구현 코드(RagClient)에 같은 예시 데이터를 넣었습니다. 비교 대상은 문제·단원·해설에 키워드가 포함되는지만 확인하는 단순 검색입니다. 과거 제품과의 성능 비교가 아닙니다.

검색 코드는 2026.05.21 팀 코드에 반영된 버전이며, 예시 문항은 이후 공개된 샘플 데이터입니다. 학년·교육과정 코드·유형·난이도 일치 여부로 결과를 확인했습니다.

Node.js 24 이상에서 node compare.mjs result.json으로 실행할 수 있습니다. 입력 질의와 전체 반환 문항, 원본 코드·데이터의 해시는 결과 파일에 남겼습니다.

제가 맡은 일

검색, 정답 검증, 문항 선택 화면을 맡았습니다

01

원하는 학년과 단원의 문항 찾기

문제·정답·해설과 교육과정 정보가 담긴 데이터를 공통 형식으로 바꾸고, 학년·단원·유형·난이도로 후보를 거르는 검색 기능을 구현했습니다. 남은 문항은 텍스트 일치도와 문항 ID로 정렬해 반환합니다.

02

표기가 달라도 같은 정답인지 비교하기

수식 표기를 검증 엔진이 읽을 수 있는 형태로 바꾸고, 정답을 비교하는 처리를 보강했습니다. 단원에 맞는 문항을 다시 찾는 흐름과 검증·결과 화면의 오류 처리도 개선했습니다.

03

만들기 전에 기준 문항을 미리 보기

선택한 단원의 예시 문제를 바로 볼 수 있도록 미리보기와 예시 데이터 생성 스크립트를 추가했습니다. 기존 문제의 풀이 구조를 유지할지, 같은 개념을 다른 형태로 물을지 고르는 화면도 정리했습니다.

검색 방식

검색 조건과 정렬 순서

아래는 팀 코드에 반영된 검색 모듈의 흐름입니다. 문항 파일은 JSONL 형식으로, 한 줄에 한 문항의 정보를 담습니다.

  1. 1. 데이터 읽기문항 파일을 읽고 사용 불가로 표시된 자료 제외
  2. 2. 형식 통일문제·정답·해설과 교육과정 정보를 공통 형식으로 변환
  3. 3. 조건 확인학년·단원·유형·난이도 등 요청 조건으로 후보 제한
  4. 4. 결과 정렬텍스트 일치도순, 같은 점수는 문항 ID순으로 반환

단어가 비슷해도 학년과 단원이 다르면 제외

학년과 교육과정 코드는 검색 점수에 섞지 않고 먼저 확인합니다. 그다음 후보 안에서 단원과 출제 의도의 텍스트 일치도를 반영합니다. 조건을 지키는 것과 후보의 순서를 정하는 일을 분리한 구현입니다.

같은 입력이면 결과 순서도 같게

점수가 같은 문항은 ID로 순서를 정합니다. 결과 순서가 바뀌어 비교를 어렵게 만드는 일을 피하고, 같은 입력의 검색 결과를 다시 확인할 수 있게 했습니다.

파일을 메모리에 읽는 방식의 한계

별도 검색 서버 없이 문항 파일로 동작하지만, 데이터를 메모리에 보관하고 검색할 때 후보를 순회합니다. 문항 수가 커질 때의 메모리 사용량과 지연은 별도 측정이 필요합니다.

다른 검색 방식과 비교해 보면

지금 구현을 돌아보면, 문장의 의미를 수치로 바꿔 비교하는 임베딩 검색에 학년·단원 필터를 함께 쓰는 방법도 대안입니다. 표현이 다른 질문을 찾는 데 유리할 수 있지만, 별도 인덱스와 운영 비용, 적합성 평가가 필요합니다.

현재 방식은 조건과 점수의 계산 근거를 코드에서 확인하기 쉽지만, 단어가 겹치지 않는 유사 표현에는 한계가 있습니다. 이 비교는 포트폴리오를 정리하며 한 사후 분석이며, 당시 두 방식을 실험해 성능 우위를 확인했다는 뜻은 아닙니다.

정답 검증

01

문자열이 다르면 비교도 달라집니다

수학 문제의 수식에는 분수나 제곱, 생략된 곱셈 기호가 들어갑니다. 화면에 보이는 표기를 그대로 계산 엔진에 보내거나 정답 문자열만 비교해서는 처리하기 어려운 경우가 있습니다.

02

입력 변환과 정답 비교를 보강했습니다

분수·제곱 표기 등을 계산 엔진의 입력 형식으로 변환하고, 필요한 곱셈 기호를 보완했습니다. 정답은 표기를 정리하고 수학 검증 엔진의 식 정리를 활용해 비교하도록 보강했습니다.

2x → 2*x
검증 엔진에 전달하기 위한 입력 변환 예시입니다. 새 성능 실험의 결과는 아닙니다.

03

변경 코드와 테스트 기록을 남겼습니다

입력 변환과 정답 비교 개선은 팀 코드에 반영됐습니다. 관련 테스트와 당시 검증·결과 화면 확인 기록을 코드 변경 이력에서 확인할 수 있습니다.

검색 예시는 10월에 기존 코드를 다시 실행한 자료입니다. 기능 개발 기간인 3~6월과 구분했습니다. 당시 테스트 기록은 개발 이력의 근거이며, 이번 문구 정리에서 제품 전체를 새로 실행한 결과는 아닙니다.

별도로 작업한 연계 기능의 개발 이력

검색 결과를 생성 단계로 넘기고 진행 상태를 화면에 보내는 작업도 별도 개발 브랜치에서 구현했습니다. 브랜치는 팀의 기본 코드와 분리해 작업하는 공간입니다.

이 변경 제안(PR #10)은 통째로 팀 코드에 반영되지는 않았습니다. 일부 전략 데이터와 계산 코드는 팀원의 별도 변경 제안(PR #11)으로 통합됐습니다. 위의 검색·검증·선택 화면 개선과는 구분합니다.

조건을 완화하는 재검색과 진행 알림(SSE)의 초기 확인 기록은 검색과 출제 의도 단계까지입니다. 이후 브랜치에 생성·검증 단계 코드도 추가됐지만, 최종 전체 경로의 실행 검증이 끝났다는 근거로 쓰지 않았습니다. 기본 코드에 반영된 후속 개선에는 단원 적합성 확인과 재검색이 포함됩니다.
